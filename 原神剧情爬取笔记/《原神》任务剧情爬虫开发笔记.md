## 《原神》任务剧情爬虫开发笔记

> 本文档记录了从零开始构建《原神》任务剧情爬虫的完整过程，包括 API 分析、数据结构解析、子任务拆分、对话树遍历、日志与报告机制等，适用于后续维护和扩展。

---

### 一、项目背景

在完成角色模块后，项目进入任务模块的开发。任务模块的目标是：

1. **获取任务列表**：从观测枢 API 获取所有任务的 ID、名称、类型、区域、版本号。
2. **获取任务详情**：对每个任务，请求详情 API，解析出子任务结构、流程梗概、详细对话。
3. **子任务拆分**：将包含多个子任务的任务拆分为独立文件，便于 RAG 检索。
4. **增量爬取**：记录已爬取的任务 ID，避免重复请求。
5. **日志与报告**：记录爬取过程中的状态，生成可追溯的爬取报告。

### 二、API 分析

#### 2.1 任务列表 API

- **URL**: `https://act-api-takumi-static.mihoyo.com/common/blackboard/ys_obc/v1/home/content/list`
- **参数**: `app_sn=ys_obc`, `channel_id=43`（任务频道）
- **响应结构**:
  ```
  data.data.list[0] → "任务" 分类
      └── list[] → 任务条目
          ├── content_id: 任务 ID
          ├── title: 任务名称
          └── ext: 包含任务类型、区域、版本号的 JSON 字符串
  ```

#### 2.2 任务详情 API

- **URL**: `https://act-api-takumi-static.mihoyo.com/hoyowiki/genshin/wapi/entry_page`
- **参数**: `app_sn=ys_obc`, `entry_page_id={任务ID}`, `lang=zh-cn`
- **核心字段**:
  - `page.modules[]`: 所有内容模块（基础信息、任务概述、任务过程、剧情对话等）
  - `page.template_layout`: 定义模块的布局和层级关系，用于识别子任务
  - `page.ext.fe_ext`: 任务分类信息（类型、区域、版本号）

### 三、子任务拆分逻辑

观测枢的任务详情页面中，一个传说任务可能包含多个子任务（幕/章）。子任务通过 `template_layout` 中的 `module_group` 层级关系来组织。

#### 3.1 数据结构示例

```json
"template_layout": {
  "tab": [{
    "module_group": [
      {
        "module_group_id": "771",
        "parent_group_id": "0",        // 顶层组（主任务）
        "module": [{ "id": "1367" }, ...]
      },
      {
        "module_group_id": "1868",
        "parent_group_id": "771",      // 子任务，继承顶层组
        "module": [{ "id": "5489" }, ...]
      },
      {
        "module_group_id": "1870",
        "parent_group_id": "771",      // 另一个子任务
        "module": [{ "id": "5505" }, ...]
      }
    ]
  }]
}
```

#### 3.2 识别规则

- `parent_group_id = 0`：顶层组（包含主任务的基础模块）
- `parent_group_id ≠ 0`：子任务组，其 `parent_group_id` 指向顶层组的 `module_group_id`
- 每个 `module_group` 中的 `module` 数组包含该子任务的所有模块 ID
- 子任务名称优先使用 `module_group.name`，若为空则从模块名称中推断

#### 3.3 模块排除

在生成子任务文件时，排除以下模块（这些模块对 RAG 问答价值较低）：
- **地图说明**
- **任务奖励**

### 四、对话树解析

任务详情中最关键的内容是 `interactive_dialogue` 组件，它包含了完整的对话树。

#### 4.1 数据结构

```json
{
  "component_id": "interactive_dialogue",
  "data": {
    "list": [{
      "root_id": "34m...",
      "child_ids": {
        "node_id_1": ["child_id_a", "child_id_b"],  // 支持分支
        "node_id_2": ["child_id_c"]
      },
      "contents": {
        "node_id_1": {
          "option": "旅行者：——啊？",
          "dialogue": "<p>法尔伽：听说在很久以前...</p>"
        }
      }
    }]
  }
}
```

#### 4.2 遍历策略

使用**深度优先遍历**，从 `root_id` 出发，按照 `child_ids` 依次访问所有节点。

**关键点**：
- 先输出 `option`（玩家选项），再输出 `dialogue`（角色台词），确保对话顺序正确。
- 遍历时记录已访问节点，避免循环（数据中一般不会出现循环，但作为安全措施保留）。
- 由于数据是树状结构，我们无法区分"主线"和"分支"，因此**遍历所有节点**，保留完整的对话内容。

#### 4.3 代码实现

```python
def parse_interactive_dialogue(components):
    # 解析 JSON...
    def traverse(node_id, visited=None):
        if visited is None:
            visited = set()
        if node_id in visited or node_id not in contents:
            return
        visited.add(node_id)
        node = contents[node_id]
        # 先 option 后 dialogue
        if node.get("option"):
            all_lines.append(clean_html_to_text(node["option"]))
        if node.get("dialogue"):
            all_lines.append(clean_html_to_text(node["dialogue"]))
        for child_id in child_ids.get(node_id, []):
            traverse(child_id, visited)
    traverse(root_id)
    return "\n".join(all_lines)
```

### 六、日志与报告机制

#### 6.1 日志配置

```python
logging.basicConfig(
    level=logging.INFO,
    format='%(asctime)s - %(levelname)s - %(module)s:%(lineno)d - %(message)s',
    handlers=[
        logging.FileHandler("logs/task.log", encoding='utf-8'),
        logging.StreamHandler()
    ]
)
```

日志输出到控制台和 `logs/task.log` 文件，包含时间戳、级别、模块名和行号。

#### 6.2 爬取报告

在爬取结束后生成 `logs/crawl_report.json`：

```json
{
  "total_tasks": 100,
  "processed": 95,
  "failed": [
    {
      "id": "508772",
      "name": "空月之歌 第十幕「道成千壑，因果异灭」",
      "reason": "无子任务"
    }
  ],
  "subtasks_saved": 230,
  "subtasks_empty": 5,
  "missing": [
    {
      "task_id": "508841",
      "task_name": "桑多涅【预告】",
      "type": "no_subtasks"
    }
  ]
}
```

通过报告可以快速定位哪些任务出现缺失，无需依赖文件名前缀。

### 九、常见问题与解决方案

| 问题                                       | 原因                                         | 解决方法                                       |
| ------------------------------------------ | -------------------------------------------- | ---------------------------------------------- |
| 对话顺序混乱                               | 直接遍历 `contents` 字典，而非按树形结构顺序 | 使用深度优先遍历 `child_ids`                   |
| 选项出现在对话之后                         | 先提取 `dialogue` 后提取 `option`            | 调整顺序：先 `option` 后 `dialogue`            |
| 子任务名称无法识别                         | `module_group.name` 为空                     | 从模块名称中推断（如“骑士之追缉”）             |
| 文件包含不需要的内容（地图说明、任务奖励） | 未过滤排除模块                               | 在 `parse_subtasks` 中过滤 `EXCLUDED` 列表     |
| 文件名包含非法字符                         | 任务名中包含 `/` 等特殊字符                  | 使用 `re.sub(r'[\\/*?:"<>|]', '_', name)` 清洗 |

### 十、后续扩展建议

1. **对话树分支选择**：当前遍历所有分支，如果希望只保留“主线”对话，可以设计策略（如始终选择第一个子节点）。
2. **性能优化**：全量爬取时，可以使用多线程并发请求（注意控制频率）。
3. **数据校验**：定期运行校验脚本，对比任务列表和实际文件数，确保完整性。
